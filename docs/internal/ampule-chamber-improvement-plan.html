Implementation-ready improvement plan

From powerful CLI to trustworthy control plane.

This plan strengthens the reliability engine first, then adds a modern local-first UI that guides new users without reducing expert control. It preserves deploy and attach modes, traffic journeys, faults, observability, agents, evidence, cleanup, report regeneration, and raw artifacts behind one consistent run model.

Program decision One core, two interfaces, zero duplicated safety logic.

The CLI and UI call the same application services. Run directories remain portable and canonical.

A platform engineer should be able to assess a local service or an existing non-production deployment without manually assembling YAML, while an expert can still inspect and control every consequential detail.

In scope

  • Trustworthy guided analysis and readiness outcomes
  • Collision-safe, resumable, auditable run records
  • Shared application services for CLI and HTTP
  • Local web control plane with run history
  • Deploy and attach setup wizard
  • Live timeline, cancellation, cleanup, findings, evidence, comparison
  • Templates and adapter capability discovery

Explicitly deferred

  • Hosted multi-tenant service and organization management
  • Distributed worker fleet or external job queue
  • Automatic production approval or deployment blocking
  • Arbitrary remote shell or user-authored command execution
  • Broad fault expansion before analysis convergence
  • Full Helm/Kustomize parity in the first UI release
Non-negotiable sequence

Four gates before broad UI execution.

The control plane may ship read-only views early, but it should not claim readiness or expose destructive controls until these contracts are proven.

Gate 1

Analysis convergence

Every live path must transform collected evidence into persisted findings and load those findings into reports.

Exit evidenceA guided deploy and attach fixture each produce a real finding from known evidence.
Gate 2

Readiness validity

The result model distinguishes ready, conditional, not ready, inconclusive, failed, and cancelled.

Exit evidenceMissing required telemetry can never yield a numeric “ready” score.
Gate 3

Run and evidence integrity

Run IDs are collision-safe; writes are atomic; evidence belongs to a manifest with run ID and digest.

Exit evidenceConcurrent same-service runs cannot share or leak artifacts.
Gate 4

Executable lifecycle

Validated state transitions, append-only events, cancel-with-cleanup, and interrupted-run handling drive both interfaces.

Exit evidenceKill-and-restart tests reconstruct accurate state and offer safe recovery.
Target architecture

A thin control plane over shared services.

Keep the first release a single local Python process bound to loopback. Add an optional UI dependency group so core CLI users do not pay for web dependencies.

Backend

Python ASGI boundary

Use FastAPI and Uvicorn in an optional ui extra. Keep domain dataclasses independent; use boundary models for HTTP validation and OpenAPI.

Frontend

Server-rendered, lightly enhanced

Jinja templates, design tokens, accessible native controls, and small vanilla JavaScript modules. Avoid a separate Node build until interaction complexity proves it necessary.

Streaming

SSE for live progress

Lifecycle and evidence events flow server-to-client; cancel, retry, cleanup, and approvals remain auditable HTTP commands.

Persistence

Filesystem canonical, SQLite derived

Run directories remain portable. SQLite indexes run summaries for fast browsing and is rebuildable from canonical artifacts.

Safety

Server-side enforcement only

The UI communicates safety gates but never owns them. Context checks, mutation policy, budgets, rollback, secrets, and cleanup stay in shared services.

Compatibility

CLI remains first-class

Existing commands keep their shape. They are reduced to argument parsing, service calls, and presentation instead of running a parallel workflow.

Canonical contracts

Make the UI a projection of durable data.

The browser should never infer run truth from filenames or prose. Every screen is backed by a versioned contract that can also be consumed by the CLI and future integrations.

run.json

Run ID, schema version, service, config hash, mode, current state, timestamps, ownership, safety policy, result status.

events.jsonl

Monotonic sequence, event ID, lifecycle transition, stage, actor, observed time, payload reference, cleanup relevance.

evidence/manifest.json

Evidence ID, producer, signal type, resource, time window, relative path, size, digest, availability, redaction.

findings.json

Finding ID, observed facts, hypothesis, severity, confidence, evidence IDs, timeline IDs, remediation, status.

result.json

Outcome, readiness score if conclusive, evidence coverage, execution coverage, rollback status, limitations, gates.

capabilities.json

Installed adapters, supported modes, prerequisites, fields, safety level, incompatible combinations, help references.

Interaction rules

  • One primary action per screen; destructive actions visually separate
  • Immediate inline validation plus one consolidated review gate
  • Every summary links to the evidence or configuration that produced it
  • Long operations always expose stage, elapsed time, cancellation, and cleanup
  • Advanced fields retain values when collapsed
  • Forms and YAML stay synchronized through one server-side spec
  • Keyboard focus, contrast, reduced motion, and screen-reader names meet WCAG 2.2 AA

Delivery plan

Eight independently shippable milestones.

Effort is expressed relatively because staffing and release cadence are not specified. Each milestone has an observable exit condition and preserves the existing CLI.

M

Trust core

Unify evidence analysis across scenario, guided deploy, and attach paths.

  • Persist typed findings in all live modes
  • Load findings into report assembly
  • Add conclusive/inconclusive outcome model
  • Remove hard-coded journey and VU report values
AcceptanceKnown bad evidence produces a finding and non-ready outcome; missing required evidence produces inconclusive, never ready.
M

Run integrity

Make run records collision-safe, atomic, and reconstructable.

  • ULID or UUID-backed run IDs
  • run.json, events.jsonl, evidence manifest
  • Atomic temp-write and rename
  • Digest verification and import validation
AcceptanceParallel run tests show no collision; stale files do not enter reports; corrupted evidence is flagged.
L

Shared application services

Extract use cases and make the lifecycle state machine executable.

  • Inspect, plan, start, cancel, resume, analyze, report
  • Single deploy/attach coordinator
  • Cancellation token and cleanup guarantee
  • CLI becomes a thin adapter
AcceptanceExisting CLI behavior passes through shared service tests; interrupted-run fixtures reconstruct valid state.
M

Read-only control plane

Launch the local server and make existing runs useful in the browser.

  • ampule-chamber ui command
  • Loopback binding and optional browser open
  • Run index rebuild and filters
  • Overview, findings, evidence, config, agents
AcceptanceArchived run directories can be imported and inspected without Kubernetes or the source repository.
L

Assessment wizard

Create and review a complete assessment without hand-editing YAML.

  • Target and mode selection
  • Immediate capability preflight
  • Traffic and fault templates
  • Advanced form/YAML synchronization
  • Manifest diff and safety receipt
AcceptanceA new user plans the sample service and an attach fixture without editing YAML; exported config works in the CLI.
L

Live execution workspace

Stream validated progress and support safe operational control.

  • SSE lifecycle and evidence stream
  • Signals and evidence coverage
  • Cancel-and-cleanup
  • Fault approval and rollback state
  • Reconnect and interrupted-run handling
AcceptanceBrowser reconnect preserves timeline; cancellation verifies cleanup; attach rollback failure blocks readiness.
M

Results and comparison

Make findings actionable, explainable, and easy to retest.

  • Outcome, score basis, coverage, limitations
  • Fact/hypothesis separation and evidence drawer
  • Compatible-run comparison
  • HTML, Markdown, JSON export
  • Retest from prior config
AcceptanceA reviewer can trace every finding and score change to registered evidence and configuration differences.
M

Templates, adapters, and hardening

Broaden supported cases through declared capabilities, not UI conditionals.

  • Template library and compatibility checks
  • Adapter descriptors and extension documentation
  • Accessibility, performance, security, packaging
  • Optional container distribution
  • Release and migration documentation
AcceptanceA new traffic or evidence adapter becomes available in the UI from its descriptor without modifying screen-domain logic.

Dependency order

Trust core → Run integrity → Application services unlocks all interactive work. The read-only control plane can begin once run contracts stabilize. Wizard and live workspace can proceed in parallel after the API boundary is fixed. Results depend on the trust core; adapter expansion waits until the first end-to-end UI release.

Measure usability without weakening reliability.

Automated verification

  • Unit tests for transitions, scoring, manifests, capabilities, redaction, path resolution
  • Contract tests proving CLI and API produce equivalent plans and run artifacts
  • Crash, reconnect, cancel, cleanup, and rollback integration tests
  • Browser tests for wizard, live SSE, evidence drill-down, compare, export
  • Accessibility checks plus keyboard-only scripted paths
  • Golden fixtures for HTML, Markdown, and JSON report consistency

Release evidence

  • Sample-service deploy run with captured screenshots and canonical artifacts
  • Observe-only attach run proving no apply/delete commands
  • Gated attach fault with verified rollback and visible safety receipt
  • Inconclusive run caused by deliberately missing metrics
  • Failed cleanup and interrupted-run recovery exercise
  • make check, UI package build, and docs verification
Performance budgets
  • Run list first render under 500 ms locally for 500 indexed runs.
  • Run detail first render under 700 ms excluding large evidence bodies.
  • SSE event visible within one second of persistence.
  • Evidence files stream on demand; never embed unbounded logs in initial HTML.
Security and local-control defaults
  • Bind to 127.0.0.1 by default; remote binding requires an explicit flag and warning.
  • CSRF protection on mutations; restrictive content security policy; no secrets in templates or event payloads.
  • Evidence is resolved by registered ID, not user-supplied path.
  • Repository access is limited to explicit roots; subprocess arguments remain structured arrays.
  • Production-like context refusal and attach mutation gates remain server-side.
Accessibility definition of done
  • WCAG 2.2 AA contrast and focus visibility.
  • All flows usable by keyboard without timing traps.
  • Live status uses polite announcements and does not rely on color alone.
  • Tables have headings; charts have textual summaries; raw evidence has accessible download alternatives.
  • Reduced-motion preference disables nonessential transitions.

Recommended first move

Ship the trust core and read-only run explorer before enabling “Run” in the browser.

That order produces immediate value—clean inspection of existing results—while forcing the run, finding, evidence, and lifecycle contracts to stabilize. Once those contracts are trustworthy, the setup wizard and live workspace become thin, safe projections of the same engine rather than a new source of orchestration risk.
