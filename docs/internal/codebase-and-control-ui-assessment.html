Architecture & product assessment

A strong engine that needs a trustworthy control plane.

Ampule Chamber already has the hard beginnings of a reliability product: live Kubernetes execution, attach mode, safety preflight, traffic, evidence collection, bounded agents, deterministic reports, and disciplined tests. The next step should be a local-first control UI— but only after closing the findings and run-integrity gaps that could make the UI communicate false confidence.

Recommendation Proceed with UI after a short “trust core” phase.

Do not build the first dashboard directly on today’s guided report output.

Priority findings

Fix trust and orchestration before polishing screens.

P0 · Trust

The guided workflow disconnects collection from analysis.

The scenario runner calls analyze_evidence, but local guided, Kubernetes deploy, and Kubernetes attach paths all write an empty findings.json. The guided report builder then sets findings=(). A successful k6 run is not the same as a reliability pass, yet the renderer scores an empty finding set as 100/100 and “ready.”

P0 · Integrity

Run IDs and evidence membership are not collision-safe.

Run directories use service name plus a timestamp with one-second precision, while callers create directories with exist_ok=True. Reports discover several evidence types by checking whether files happen to exist, not through a run-owned evidence manifest. A repeated run can reuse a directory and surface stale evidence. A sampled local run in this workspace was rendered with attach discovery, rollback, and Prometheus references—exactly the category mismatch an immutable manifest should prevent.

P1 · Cohesion

Two live paths have different capabilities and result semantics.

ampule-chamber run --scenario owns the mature evidence-analysis-report flow for kind scenarios, while assess --mode kubernetes owns the newer deploy/attach flow. A UI over both would need to explain inconsistent inputs, supported faults, artifacts, and scoring. Consolidate them behind one application service before adding another adapter.

P1 · Contract

Scenario and ChamberConfig models overlap without one canonical schema.

The repository supports kind: Scenario and kind: ChamberConfig with different concepts and validators. Planning reads only the first traffic journey, even though Kubernetes execution can run multiple journeys; the report also presents the first journey and hard-codes max virtual users to 1. A form-based UI will expose these inconsistencies quickly.

P1 · Runtime

The lifecycle model is defined but not driving execution.

A thoughtful state machine exists—created, ready, baseline, experiment, fault, recovery, analysis, reporting, terminal states—but the guided workflow persists ad hoc stage strings. The UI needs validated transitions, progress events, cancellation, crash recovery, and cleanup status. Make the existing lifecycle the executable contract and persist an append-only event log.

P2 · Maintainability

The 3,342-line workflow module is becoming the product boundary.

CLI parsing, config inference, validation, planning, deploy/attach execution, k6 generation, evidence collection, Prometheus access, faults, agents, persistence, and report assembly live together. This is still testable, but a control UI would add HTTP, jobs, streaming, and user state to the same module unless the application layer is extracted now.

Recommended architecture

One core, three adapters.

Keep the system local-first and single-process for the first UI. The browser, CLI, and future CI integration should call the same typed application services. Avoid a queue or microservice fleet until concurrent multi-user operation is a proven requirement.

Immutable run store

Run directories remain canonical

Add run.json, events.jsonl, and evidence/manifest.json with hashes. A small SQLite database may index runs for fast UI lists, but it must be rebuildable from directories.

Use a shared service, not CLI subprocesses

Extract typed use cases from workflow.py. Both CLI handlers and HTTP routes call them directly, preserving identical safety checks and result semantics.

Stream events with SSE first

Run progress is predominantly server-to-client. Server-sent events are easier to operate and reconnect than WebSockets; commands such as cancel remain ordinary HTTP requests.

Single background worker for MVP

Start with an in-process worker and a lock that makes concurrency explicit. Persist every transition so interrupted runs can be shown as interrupted and offered cleanup or resume.

Schema drives forms and validation

Publish JSON Schema for one canonical assessment spec. Add UI metadata for labels and help text, but keep validation and safety rules server-side.

Capabilities drive portability

Each environment, traffic, fault, and observability adapter declares supported operations and prerequisites. The UI disables unsupported combinations before a run is planned.

Starter templates

  • HTTP baseline and saturation
  • Dependency slow, unavailable, 429, or 500
  • Pod restart and replica loss
  • Memory growth and OOM investigation
  • Retry amplification and recovery
  • Queue backlog and drain

Every template declares

  • Compatible target and traffic types
  • Required tools, RBAC, and telemetry
  • Mutation level and cleanup contract
  • Maximum duration and load budget
  • Required evidence for a conclusive result
  • What “pass,” “risk,” and “insufficient evidence” mean
Implementation sequence

Build confidence in six bounded slices.

Each slice leaves the CLI usable and adds a testable contract. Avoid expanding fault types until the common execution-and-analysis path is trustworthy.

Trust core

Run collected evidence through analysis in every live path, load persisted findings into reports, add evidence-completeness outcomes, and remove hard-coded traffic summaries.

Done when: a guided run can produce real findings, and missing required telemetry cannot render “ready.”

Immutable run record

Use collision-proof IDs, atomic writes, append-only lifecycle events, and an evidence manifest containing type, producer, timestamps, run ID, size, and digest.

Done when: reruns never reuse directories, and reports ignore stale or unregistered files.

Application-service extraction

Unify scenario and guided execution behind typed plan, start, cancel, analyze, and report services; make the lifecycle state machine executable.

Done when: CLI tests call the same use cases the UI will call, with no CLI subprocess wrapper.

Local control API and runs screen

Add local HTTP endpoints, SSE events, a rebuildable run index, interrupted-run recovery, and read-only screens for run history and existing results.

Done when: ampule-chamber ui opens a browser and can inspect imported/current run directories.

Setup wizard and live run

Add target selection, generated-config review, capability preflight, manifest diff, exercise builder, safety receipt, live timeline, and cancel-with-cleanup.

Done when: the sample service and one attach target can be assessed end-to-end without editing YAML.

Results, comparison, and extensibility

Add evidence-backed findings, coverage, timeline, service graph, raw artifacts, baseline comparison, HTML export, templates, and adapter capability discovery.

Done when: a user can explain what changed between two runs and add a new adapter without changing UI domain logic.

Do not build yet

  • A separate frontend/backend deployment topology
  • A distributed job queue before concurrency is needed
  • A new findings model exclusive to the UI
  • More fault primitives before analysis is unified
  • Automatic deployment gates based only on the current score

First release acceptance

  • One-command launch and prerequisite check
  • Deploy and observe-only attach workflows
  • Plan review and explicit safety confirmation
  • Validated live state, cancellation, and cleanup
  • Findings tied to immutable evidence IDs
  • “Insufficient evidence” instead of false readiness

Scope and limitations
  • Reviewed tracked source, tests, public documentation, all phase summaries, current phase plans, and sampled local run artifacts.
  • Did not run a live Kubernetes assessment or inspect an external service repository.
  • Did not perform a security audit; safety observations are architectural and based on existing guardrails.
  • The control-screen visual is a code-native concept embedded in this report, not an implemented product UI.
Bottom line

The shortest path to “easy for many cases” is not more options—it is one trustworthy run model with guided templates.

First unify evidence, findings, readiness, lifecycle, and persistence. Then place a thin local web control plane over the shared services. This preserves the repository’s strongest qualities—safety, evidence, repeatability, and tests—while making the chamber approachable to users who should not need to understand its YAML or internal phases.
